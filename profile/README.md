<h2>二、浏览器环境这一栏怎么勾</h2>
<img src="/tp.png" alt="浏览器环境代理与账号分组的一致性检查表">
<p>浏览器环境要回答一个问题：如果我关掉代理，这个 profile 还能不能暴露"我是谁"。常见漏洞有三个——WebRTC 泄露本地内网地址、DNS 绕开代理直连、以及字体与 Canvas 指纹在所有 profile 里完全一致。前两个能靠设置解决，第三个需要用独立 profile 目录，而不是同一个浏览器开多个窗口。</p>
<h3>profile 目录要不要按账号重建</h3>
<p>新号建议新建目录，别从老号复制。复制会把 Cookie、本地存储、缓存的站点数据一并带过去，等于让两个号共享一段历史。迁移老号时若必须复制，至少清掉 Local Storage 与 IndexedDB，并在新环境静置一天再操作。</p>
<h3>时区、语言、地理位置这三项为什么要一起改</h3>
<p>只改时区不改语言，或只改语言不改地理位置权限，都会出现内部矛盾。审查方看到的是一组信号，一致性比单项精度更重要。做法是按出口城市设定：时区跟随城市，语言按该城市主流语言排序，地理位置权限设为"拒绝"或与出口一致，别留空白。</p>

<h2>三、代理层与账号分组的对应关系</h2>
<p>分组的意义是让"谁在用哪条出口"这件事可查。最小可用方案是按项目分组，组内按账号编号绑固定出口，编号规则建议"项目两位 + 序号三位"，例如 IP01-007。编号写进代理配置文件名、浏览器目录名和登记表，一处改三处同步。</p>
<h3>白名单和账号密码，哪种鉴权更适合团队</h3>
<p>固定办公出口的团队用 IP 白名单最省事，配置里不用带密码，泄露风险低；远程办公或成员 IP 会变的，用账号密码加子账号，好处是能按人回收权限。两者也可以叠加：白名单兜底，子账号做区分。</p>

<h2>四、上线后每天复查的三项</h2>
<p>配置不是一次性工作。每天花三分钟看三件事：出口是否还是登记的那个 IP、账号有没有新增验证提示、代理日志里有没有异常重连。前两项决定要不要干预，第三项决定要不要换线路。</p>
<h3>异常重连多少次算不正常</h3>
<p>按天统计，单条出口重连超过五次就值得看一眼，超过二十次基本可以判定线路不稳。注意区分"客户端主动重连"和"服务端断开"：前者多半是本地网络抖动，后者要看服务商的节点负载。</p>

<h2>五、什么情况下要推翻重配</h2>
<p>三种情况建议整体重配而不是打补丁：一是发现同一条出口上曾有别人的账号（历史污染）；二是浏览器 profile 目录被多人共用过（Cookie 已混）；三是账号资料国与出口国出现不可调和的矛盾（比如支付方式只能绑某国）。打补丁在这些场景里通常只是把问题往后推。</p>

<h2>常见问答</h2>
<h3>九项必须全过才能开工吗？</h3>
<p>答：出口类和环境类建议全过，管理类可以先简后繁。比如留痕可以先用手写表格，等账号多了再接日志系统。但 Cookie 隔离和 DNS 出口这两项不能省。</p>
<h3>用指纹浏览器还需要单独配代理吗？</h3>
<p>答：需要。指纹浏览器解决的是浏览器侧信号，代理解决的是网络侧出口，两者不能互相替代。它通常只是把代理配置做得更方便，出口质量仍取决于你买的资源。</p>
<h3>同一条出口能给同一项目的两个号用吗？</h3>
<p>答：不建议。同项目同出口等于把两个号放在同一网络身份下，一旦其中一个出问题，另一个会被一起看。资源紧张时可以错峰使用，但要接受关联概率上升。</p>
<h3>清单多久重跑一次？</h3>
<p>答：新环境上线前必跑，成员交接必跑，换服务商必跑。稳定运行期间每月抽查一次即可，重点看 DNS 与 WebRTC 两项，它们最容易在浏览器升级后失效。</p>
